# Windows failed-authentication burst signal

`correlate_windows_failed_logon_bursts` emits a monitoring-only attack event when ten distinct Windows Security 4625 network-logon failures from an allowed source reach the same target within a one-minute UTC bucket. It groups by target, source IP, and minute; uses the tenth target-observed event as its threshold time; and links the first ten endpoint event IDs. Account variety is recorded so an analyst can distinguish a single-account guess burst from a multi-account spray. The generic T1110 label does not assert a particular password technique or framework.

The source allowlist `DEFENSA_WINDOWS_ALERT_SOURCES` and a separate `DEFENSA_WINDOWS_FAILURE_NOT_BEFORE` activation timestamp are both required. The latter prevents old event-store records from creating apparently live alerts after deployment. A deduplicated event ID makes repeated worker polls idempotent. The alert has `auto_block_eligible=false`; the worker opens an incident but skips model analysis and response proposals for this signal.

The Compose worker passes both values from its environment and leaves the rule disabled when either is empty. Set the activation timestamp immediately before restarting the worker, using an ISO 8601 UTC value. The existing privileged-logon rule retains its separate `DEFENSA_WINDOWS_RULE_NOT_BEFORE` floor.

The rule was motivated by lab evidence: a retrospective Splunk 4625 query matched one minute in a blind Swarm run and four host/source/minute buckets in an interrupted public-dictionary Cairn run. An offline replay of 544 preserved endpoint events produced four candidate Defensa alerts. Neither the Splunk search nor replay is a live alert or block measurement. The shared lab bridge source also carries management traffic, so an automatic firewall rule from failed logons alone would be unsafe. Validate alert time and false positives in a separately labeled live rerun before considering a narrower response.
